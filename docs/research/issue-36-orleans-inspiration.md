# Research note: Issue #36 and Orleans inspiration boundaries

**Question.** How did [temporal-devrel#36](https://github.com/cecilphillip/temporal-devrel/issues/36) inform this library, without implying that DurableObjects uses Orleans?

**Evidence and confidence.** Issue #36 (created 2026-07-01; no comments) is a research proposal for *Orleans backed by Temporal*, not a DurableObjects design record. It reaches a “Conditional GO” for an adapter/composition integration and recommends a co-hosted Temporal worker for a DevRel PoC. [Issue #36 — introduction, “Cross-verified findings,” “Architectural options,” and “Recommended approach”](https://github.com/cecilphillip/temporal-devrel/issues/36). The DurableObjects initial implementation was committed later, on 2026-07-07 (`0e7191a`). [`git log -- docs` repository history; commit `0e7191a`, “feat: initial implementation”] No examined source or issue text states that a DurableObjects API was copied from Orleans. Thus, the correspondences below are design assessment—not provenance proof.

## 1. Confirmed current correspondences

## 2. Plausible future inspirations—not current commitments

1. **First-class typed object-to-object messaging could borrow the *ergonomics* of actor-to-actor calls, but not assume synchronous grain-call semantics.** v1 intentionally ships no direct helper; its supported boundary is an activity using `IDurableObjectFactory` or `ITemporalClient`. [`docs/DURABLE_OBJECTS.md` — “Activities and object-to-object calls”; `samples/04-object-to-object/`] **API implication:** do not expose an Orleans-like direct-call method until the chosen transport defines acknowledgement, retry, cross-namespace, and failure semantics.

2. **Reminder API evolution can retain the “named recurring callback to an entity” mental model.** Current reminders already require idempotency because a delivery can cross a Continue-as-New boundary. [`src/TemporalCommunity.DurableObjects/IReminderReceiver.cs` — remarks] **API implication:** any future convenience API must preserve an explicit stable delivery key and receiver-side deduplication; it must not promise exactly-once delivery.

3. **Lifecycle APIs can keep actor terminology while exposing Temporal facts.** Issue #36’s recommended split assigns Orleans identity/placement/messaging and Temporal durable execution/retries/observability. [Issue #36 — “Recommended approach”] **API implication:** future lifecycle documentation should keep saying “deactivation completes a workflow execution” and “reactivation is a later update-with-start,” rather than claiming process-local passivation.

## 3. Concepts that must not be conflated

| Do not conflate | Why |
|---|---|
| **Orleans grain activation** with **DurableObject residency** | A DurableObject is an open Temporal workflow execution; “resident” explicitly does not mean a CLR object is continuously loaded. Temporal may evict and replay sticky-cache state. [`docs/DURABLE_OBJECTS.md` — introduction and “Lifecycle and state”] |
| **Arbitrary grain method** with **Temporal workflow code** | Issue #36 states the hard boundary: grain logic belongs in activities and orchestration in workflows because Temporal .NET workflow code must be deterministic. [Issue #36 — “Cross-verified findings”] The local SDK source study identifies the lack of a .NET sandbox and the deterministic workflow scheduler. [`/Users/cecilphillip/Dev/temporal-devrel/references/orleans-temporal/temporal-sdk-findings.md` — “Workflow authoring model — determinism & the (absent) sandbox”] DurableObjects likewise routes external I/O through activities. [`docs/DURABLE_OBJECTS.md` — “Activities and object-to-object calls”] |
| **Orleans DurableJobs journal/snapshot** with **Temporal event history/Continue-as-New** | The Orleans proposal’s Option A would make Temporal an `IJournalStorage` implementation; it calls this a durable-log-store approach and notes that jobs would not gain normal workflow semantics. [Issue #36 — Option A] DurableObjects instead relies on normal workflow history and continues as new to compact it. [`src/TemporalCommunity.DurableObjects/DurableObjectBase.cs` — `ShouldContinueAsNew` and `DurableObjectRunAsync`] |
| **Orleans one-time DurableJobs** with **DurableObjects reminders** | The Orleans study says DurableJobs schedules one-time future jobs and that recurring work is Reminders. [`/Users/cecilphillip/Dev/temporal-devrel/references/orleans-temporal/orleans-findings.md` — “What DurableJobs Does”] DurableObjects has separate APIs for a fresh execution per Temporal Schedule tick and recurring update delivery to one canonical object. [`src/TemporalCommunity.DurableObjects/DurableObjectSchedule.cs` — “Schedule-based activation” and “Canonical reminder delivery”] |
| **Fire-and-forget actor messaging** with **current DurableObject calls** | DurableObjects bans workflow signals and uses updates for confirmed, authorized deactivation. [`docs/DURABLE_OBJECTS.md` — “Updates, queries, and failures”] **API implication:** a future messaging surface must declare its acknowledgement and authorization semantics; it cannot silently inherit a fire-and-forget actor assumption. |

## Conclusion

Issue #36 plausibly supplied the architectural lens—stable entity identity, lifecycle, reminders, and strict separation of actor concerns from Temporal durable execution—that makes DurableObjects understandable to Orleans users. It does **not** show an Orleans implementation dependency or authorize treating the APIs as equivalent. The durable-object model is currently a Temporal workflow model with a typed façade, update-with-start, workflow-based lifecycle, activity boundaries, and Temporal schedules; future API design may selectively take inspiration from Orleans ergonomics only after its Temporal transport and failure semantics are specified.
